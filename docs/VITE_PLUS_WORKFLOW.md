## Portable E2E preview port

`PLAYWRIGHT_PORT` optionally changes the configured E2E preview port; the default remains 4173. When another process owns it, run `PLAYWRIGHT_PORT=4573 pnpm test:e2e` or `PLAYWRIGHT_PORT=4573 pnpm test:seo`. The configuration aligns baseURL, the preview command and media ORIGIN; maintenance tests resolve their URLs against that configured origin. For authenticated runs, align the `ORIGIN` passed to the local seed script too. This adds no toolchain dependency or upgrade. `pnpm check:css` also runs the runtime font-source policy check; the browser font/TOC regressions are collected by the existing E2E script.

## Commands: project scripts and Vite+ built-ins

Run project scripts through pnpm. `pnpm exec vp <command>` invokes the locally installed Vite+ built-in; `pnpm exec vp run <script>` asks Vite Task to run the named project script. Built-ins and project scripts can have different behavior ([official Vite+ run guide](https://viteplus.dev/guide/run)). In particular:

| Intent                                  | Command                                      | What it actually does here                                                                                                                                                              |
| --------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Install the locked project dependencies | `pnpm install --frozen-lockfile`             | Uses pnpm and the existing lockfile. For an isolated checkout with a complete local store, `--offline` may be added.                                                                    |
| Start development                       | `pnpm dev`                                   | Runs the `dev` script, currently `vp dev`. Add `--open` if desired.                                                                                                                     |
| Svelte and TypeScript diagnostics       | `pnpm check`                                 | Runs `svelte-kit sync` and `svelte-check`; it is the repository's Svelte/type gate.                                                                                                     |
| Format, lint and Svelte lint            | `pnpm lint`                                  | Runs `vp fmt --check .`, `vp lint .`, then ESLint on `**/*.svelte`. Do not drop the ESLint step: the migration recorded that it enforced Svelte-specific rules not exercised by Oxlint. |
| Format owned files                      | `pnpm exec vp fmt path/to/file`              | Uses Oxfmt with the `fmt` block in `vite.config.ts`. Inspect the affected diff; don't format other people's changes. Use `--check` to check without writing.                            |
| Run unit and component tests            | `pnpm test:unit --run`                       | Runs the project's `vp test` unit/browser projects once. The browser project needs Playwright's installed browser and a usable local port.                                              |
| Run one Vitest spec                     | `pnpm exec vp test run path/to/file.spec.ts` | Runs the Vite+ test built-in for that filter. Add the appropriate project filter when needed; confirm actual collected tests.                                                           |
| Build the production application        | `pnpm build`                                 | Runs **both** `vp build` and `node scripts/maintenance-build.mjs`. Use this complete script for release, preview, SEO and maintenance verification.                                     |
| Preview a production build              | `pnpm preview --port 4173`                   | Runs the preview script after `pnpm build`; its local router is not the Vercel deployment router.                                                                                       |
| Check prerendered output                | `pnpm check:pages`                           | Run after `pnpm build`; checks the repository's prerendered-page contracts.                                                                                                             |
| Run the SEO browser gate                | `pnpm test:seo`                              | Runs `tests/seo/seo-standard.spec.ts`. The script is `test:seo`, not `seo:test`.                                                                                                        |
| Run the complete E2E suite              | `pnpm test:e2e`                              | Runs `playwright install` and then Playwright tests. `pnpm exec playwright test` runs the configured tests without the install step when the required browsers are already installed.   |
| Run both project test scripts           | `pnpm test`                                  | Runs `test:unit --run` and then `test:e2e`; this is broader than the `vp test` built-in.                                                                                                |

**Do not replace `pnpm build` with `pnpm exec vp build` for this project's complete build.** The built-in bypasses the package script and therefore skips the maintenance-output step. Likewise, `pnpm exec vp test` does not run the E2E part of `pnpm test`, and `pnpm exec vp check` does not replace `pnpm check` plus `pnpm lint`: this repository sets `lint.options.typeCheck: false`, and the project lint script separately runs ESLint on Svelte files. Vite+'s [check guide](https://viteplus.dev/guide/check) describes its general capabilities; the actual `vite.config.ts` and scripts decide what runs here.

Use targeted checks as work progresses and the full gate when the task or repository playbook requires it. Never lower a threshold, skip a required suite, or report an unrun check as passed. If a full command fails on an unrelated existing file, identify the failure and run unaffected checks separately; do not reformat unrelated work merely to obtain a green result.

## Authoring rules

- In `vite.config.ts`, use supported `vite-plus` exports such as `defineConfig` and `lazyPlugins`. For test APIs use `vite-plus/test` and the appropriate `vite-plus/test/browser*` entry; the current Playwright provider is `vite-plus/test/browser-playwright`.
- Do **not** mechanically replace every `vite` import in application or plugin code: Vite+'s [migration rules](https://viteplus.dev/guide/migrate-rules) limit the Vite config rewrite, and some upstream exports remain on `vite` or `vite/rolldown`. Module augmentations for `vite`, `vitest` and `@vitest/browser*` retain their upstream module identities. The community WebdriverIO provider, if ever introduced, uses `@vitest/browser-webdriverio`.
- Keep the current catalog references, overrides, browser-provider dependency and peer rules unless a scoped change and tests justify changing them. The installed Vite+ runner resolves its bundled Vitest first; keep `vitest` and the official browser provider aligned with the version it bundles. The failed 5.1.0-only upgrade is documented in `CHANGELOG.md`.
- `vitest-browser-svelte`'s `render(...)` returns a promise in this project; await it. Vitest 5 changed behavior including mock clearing, test-name matching and inline project inheritance. Check the [Vite+ Vitest 5 guide](https://viteplus.dev/guide/vitest-v5) and [Vitest migration guide](https://vitest.dev/guide/migration/) when changing tests or upgrading; preserve the tests' intent and coverage.

## TypeScript and editor recovery

The committed `tsconfig.json` extends `$app/tsconfig` and lists `$app/types`, `node` and `vite/client`. The installed SvelteKit 3 sync code generates the `$app` packages under `node_modules`; do not replace this with a SvelteKit 2-era `.svelte-kit/tsconfig.json` path or commit generated files. If those types cannot be found after cloning or changing branches:

1. Run `pnpm install --frozen-lockfile` to restore the declared development dependencies, then `pnpm check` to regenerate SvelteKit types and run Svelte diagnostics. Investigate installation/sync failures rather than suppressing missing types.
2. In VS Code, select **TypeScript: Select TypeScript Version → Use Workspace Version**, then **TypeScript: Restart TS Server** if diagnostics remain stale. `.vscode/settings.json` points at the installed SDK and enables the workspace-version prompt. Keep the recommended Svelte extension enabled. See [VS Code's TypeScript version guidance](https://code.visualstudio.com/docs/typescript/typescript-transpiling#_using-newer-typescript-versions).
3. `pnpm exec tsc --noEmit` is a useful supplementary check; `pnpm check` remains required for Svelte files. Both commands include `src`, `scripts` and `tests` through the root config. Plain TypeScript sees Svelte's ambient `*.svelte` fallback rather than the component's generic declaration. When a test needs a concrete generic component, specialize it in a small typed Svelte fixture (see `src/lib/components/ui/__tests__/CatalogGridFixture.svelte`), then render that fixture. Do not cast to `any`, suppress errors or remove props checks. See [Svelte's TypeScript and generic-props documentation](https://svelte.dev/docs/svelte/typescript).

## Authenticated browser verification

The homepage and CMS blog use request-time SSR for automatic publication discovery (owner requirement, 2026-11-05). `pnpm check:pages` covers the remaining static output; raw-HTML and browser tests separately verify homepage/blog cards. A lower static page count caused by this documented rendering change is not a skipped homepage check. Preserve the full build, all SEO/CWV thresholds and authenticated E2E.

The admin suites skip when `E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD` are absent. Report those skips; they do not verify admin behavior. For a complete local run, use an isolated worktree, a throwaway account and `DATABASE_URL=pglite://e2e` for both seeding and Playwright. This selects the local `.svelte-kit/pglite-blog` file. The default `memory://e2e` creates a fresh in-memory database and cannot share a seeded account with the preview process.

Generate a unique throwaway email for each run: login rate-limit state persists for 15 minutes even after the account is revoked. Set `ADMIN_SEED_EMAIL` / `ADMIN_SEED_PASSWORD`, matching `E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD`, and local auth/password secrets in the process environment. Follow [the seed workflow](ADMIN_LOCAL_LOGIN.md), run `pnpm db:seed-admin`, then `pnpm test:e2e` with the same environment and `ORIGIN=http://localhost:4173`. Keep `MEDIA_STORAGE=disk` for the configured local preview. Revoke the test account with `pnpm db:seed-admin --revoke` after Playwright stops, including after failures. Never point these tests at production, reuse real credentials or commit generated data. Assert the current launch-gate policy for published blog routes; a published post can still be excluded from the sitemap while `/blog` is gated.

The full `pnpm test:e2e` suite also exercises the generated Vercel handler directly in an isolated child process (`tests/deployment/vercel-runtime.e2e.ts`). Keep this deployment regression: Vite preview can serve generated remote-prerender assets that are unavailable to a deployed SSR function. Runtime-callable remote prerender functions need the documented `dynamic` option; build success and local preview HTTP200 do not establish hosted SSR readiness.

## If a Vite+ upgrade is explicitly requested

1. Inspect the worktree and coordination registry; preserve existing changes. Record current Node/pnpm versions, scripts, catalog, overrides, installed toolchain and relevant baseline checks. Read the [project update guide](https://viteplus.dev/guide/upgrade-project), [migration guide](https://viteplus.dev/guide/migrate), [migration rules](https://viteplus.dev/guide/migrate-rules) and [Vitest 5 guide](https://viteplus.dev/guide/vitest-v5). This project already uses Vite+: do not scaffold it or repeat first-time setup.
2. Choose the requested target release and use a compatible Node runtime. Before changing dependencies, inspect that target CLI's help and run its migrator from the workspace root via pnpm, for example `pnpm dlx --package=vite-plus@<target-version> vp help migrate`, then `pnpm dlx --package=vite-plus@<target-version> vp migrate --no-interactive`. `pnpm dlx` may need registry access; it is not necessary for routine work. Use the [documented preview registry](https://viteplus.dev/guide/migrate) only when a preview is explicitly requested. Do not use this project's older local `vp` as the target migrator for a different version.
3. Existing Vite+ projects use the normal upgrade flow; do not pass `--full` unless the user requests first-time setup again. Check the target CLI's help for supported options. Preserve existing agent/editor/hook policies; do not install hooks or overwrite instructions without authorization. Do not pre-upgrade Vitest, the manifests or lockfile before the target migrator can identify the existing runner.
4. Resolve every `BLOCK`, review every `REVIEW` and manual follow-up even on a successful exit, and inspect the diff. Keep package-manager catalogs, alias and compatible runner/provider pins aligned. Preserve project-specific settings, Svelte ESLint coverage, scripts and user changes.
5. Keep any generated Vitest-v4 or tsdown compatibility settings and comments for the first validation run. Run the repository's actual gates (`pnpm check:css`, `pnpm check`, `pnpm lint`, `pnpm test:unit --run`, `pnpm build`, `pnpm check:pages`, `pnpm test:seo`, and the applicable Playwright E2E suites), plus any configured coverage or benchmark checks. `pnpm exec vp check` can supplement these checks, not replace them. Record commands, counts, skips, warnings and failures.
6. Only after a passing baseline, review any _newly generated_ compatibility settings one at a time using the official linked guidance. Remove a setting and its generated comment only when the same affected tests still run and pass without new skips or weakened assertions; otherwise restore both. Preserve pre-existing or unclear settings. For `fakeTimers.toNotFake`, remove only a newly added `Temporal` entry and preserve the other exclusions. Keep glob-threshold `perFile: true` unless the owner explicitly approves a change. Re-run the relevant suites after each trial and the full required validation with accepted removals combined; report the disposition and evidence for each candidate.
7. If the project later gains a library `pack` configuration, follow the [tsdown 0.23 release notes](https://github.com/rolldown/tsdown/releases/tag/v0.23.0), run `vp pack` and consumer checks after each candidate change, and check emitted imports and declarations. Removing generated `deps.resolveDepSubpath: true` changes external subpath resolution; removing `attw.profile: 'strict'` adopts an `esm-only` profile that omits Node 10 and CommonJS resolution checks. Retain settings when required consumer support or validation is unclear.

Don't perform a migration, install, upgrade, formatting sweep, commit or push just because you read this document. Follow the task's scope and report what was actually verified.
